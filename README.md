## 4. Теория и реализация (Примеры из кода)

### 4.1. Слоистая архитектура и инкапсуляция FS

**Теория:** Для обеспечения масштабируемости проекта применена слоистая архитектура. Логика работы с жестким диском (модуль `fs`) строго изолирована в низкоуровневом `fileService`. Это позволяет бизнес-логике (`savesService`) не зависеть от конкретного способа хранения данных. `fileService` оборачивает чтение и запись в блоки `try...catch` для предотвращения падения сервера при ошибках файловой системы.

**Пример из кода (Изолированный файловый сервис):**

```javascript
// services/fileService.js
// ...
const readData = (filePath) => {
  try {
    const data = fs.readFileSync(filePath, "utf8");
    return JSON.parse(data);
  } catch (err) {
    console.error("Ошибка чтения файла:", err);
    return [];
  }
};
// ... экспорт
```

### 4.2. Маршрутизация и обработка JSON

**Теория:** Прием сырых текстовых данных от клиента по сети требует предварительного парсинга. Для этого на уровне инициализации приложения (до объявления маршрутов) применяется встроенный Middleware `express.json()`. Маршрутизация конкретной сущности (Приказов) вынесена в отдельный модуль с помощью `express.Router()`, что позволяет избежать перегрузки главного файла `index.js`.

**Пример из кода (Подключение Middleware и Роутера):**

```javascript
// index.js
app.disable("x-powered-by"); // отключаем заголовок о версии для безопасности

app.use(express.json());

app.use((req, res, next) => {
  console.log(`[${new Date().toISOString()}] ${req.method} ${req.url}`);
  next();
});

app.use("/saves", savesRouter);
```

### 4.3. Обновление данных через Spread-оператор

**Теория:** Для реализации обновления приказа применяется метод HTTP `PATCH`, подразумевающий частичное изменение ресурса. На уровне `savesService` используется Spread-оператор (`...`). Сначала "распаковывается" старый объект приказа, а затем поверх него "распаковывается" объект с новыми данными (`saveData`), переданный клиентом. Благодаря правилу перезаписи свойств с одинаковыми ключами, обновляются только целевые поля, а остальные (например, `id` или `description`) остаются нетронутыми.

**Пример из кода (Логика обновления в Сервисе):**

```javascript
// services/ordersService.js
const update = (id, saveData) => {
  const saves = fileService.readData(dataFilePath);
  const index = saves.findIndex((s) => s.id === id);

  if (index === -1) return null;

  saves[index] = { ...saves[index], ...saveData };
  fileService.writeData(dataFilePath, saves);

  return saves[index];
};
```

## 5. Вывод

В ходе выполнения лабораторной работы были получены практические навыки разработки бэкенда на платформе Node.js. С использованием фреймворка Express был спроектирован и запущен локальный сервер, предоставляющий полноценный REST API для предметной области «Приказы ректора».

Проект был структурирован согласно паттерну Layered Architecture: ответственность строго разделена между контроллерами (обработка HTTP-запросов) и сервисами (бизнес-логика и файловые операции). Успешно реализовано персистентное хранение состояния приложения в формате JSON-файла с использованием встроенного модуля `fs`.

Также были на практике применены концепции промежуточного программного обеспечения (Middleware) для парсинга тела запросов и логирования, а методы тестирования API автоматизированы с помощью Postman, результатом чего стала экспортированная коллекция запросов.
